# pi-im-relay

**用 QQ / 微信 驱动你本机正在运行的 AI coding agent。**

手机上发一句话，本机的 agent 去读你的文件、跑你的命令，结果回到聊天窗口。

```
QQ 用户 ──► 腾讯 ──► NapCat（本机登录 QQ）── ws://127.0.0.1:3001 ──┐
                        ▲                                          │
                        └── http://127.0.0.1:6099（WebUI 取二维码）  │
                                                                   ├─► pi-im-relay ─► pi agent ─► 你的项目
微信用户 ──► 腾讯 iLink 云 ── HTTPS 长轮询（纯出站）───────────────┘        ▲                │
                                                                          └── 最终答复 ◄────┘
```

一句话说清它的定位：**不改动你的 agent 使用习惯，只是给它加一个手机入口。**

---

## 它能做什么

| 能力 | 说明 |
| --- | --- |
| 🔐 扫码登录 | QQ / 微信的二维码**直接出现在对话里**，用手机扫一下即可，全程不用切界面 |
| 🔁 换号 | 发一次「QQ登录」就自动踢掉旧账号、清登录票据、重启并出新码；微信同理 |
| 🔥 配置热加载 | 改 `config.json` 自动生效，不用重启、不用敲命令 |
| 📄 长文转 PDF | 长结论渲染成排版好的 PDF 发回来，聊天里只留一段简短说明 |
| 🖼 收图入相册 | 用户发来的图片自动落盘、按内容去重，回执里带完整路径 |
| 🧠 记忆注入 | 工作约定 + 身份定位 + 最近聊天记录 + 空间说说，长会话不失忆 |
| 📎 文件出站 | 把本机任意文件作为附件发到聊天 |
| ⚡ 进度可控 | 可以实时回报每一步，也可以只回最终结果 |
| 🎭 账号经营 | 头像、昵称、签名、在线状态、空间说说都能程序化维护（见第四部分） |

# 第一部分 · 新手教程

## 0. 先确认你有这些

- 一台**常开**的机器（家里的电脑就够，不需要服务器、不需要公网 IP）
- 一个能用起来的 AI coding agent（本项目以 [pi](https://github.com/earendil-works/pi-coding-agent) 为宿主）
- 手机上装着 QQ 或微信

## 1. 安装

```bash
# 从本地目录装
pi install /path/to/pi-im-relay

# 或从 git 装
pi install git+https://github.com/<your-account>/pi-im-relay.git
```

也可以在 `<agentDir>/settings.json` 里手动加一行（`<agentDir>` 默认是 `~/.pi/agent`）：

```json
{ "packages": ["..\\pi-im-relay"] }
```

装完**重启一次 agent**（或执行 `/reload`）。这是唯一一次需要手动重载 —— 之后改配置都会自动生效。

## 2. 确认它起来了

```
/im status
```

应当看到类似输出：

```
🟡 QQ：needs-login — NapCat 已启动，但 QQ 还没登录
🟡 微信：off — 未启用
```

首次启动会自动在 `<agentDir>/im-relay/config.json` 生成一份默认配置。

## 3. 接入 QQ

QQ 侧需要一个 **OneBot11 实现**来充当协议端，推荐 [NapCat](https://github.com/NapNeko/NapCatQQ)（基于官方 QQNT 内核）。

### 3.1 安装并启动 NapCat

从 [Releases](https://github.com/NapNeko/NapCatQQ/releases) 下载对应平台的版本，解压，启动它。

**先不要在 NapCat 自己的界面里登录** —— 下一步在对话里扫。

### 3.2 在对话里扫码登录

在聊天框里直接说：

```
QQ登录
```

或者敲命令 `/im login qq`。二维码会**直接出现在对话里**：

| 界面类型 | 二维码怎么显示 |
| --- | --- |
| 支持图片的界面 | 作为一张 PNG 出现在对话流里，手机直接扫 |
| 终端界面 | 用半块字符 `▀▄█` 画在编辑器上方，屏幕可扫 |
| 纯文本模型 | 退化成代码块里的 ASCII 二维码，或直接给链接 |

用手机 QQ 扫码并在手机上确认。确认后通道会自动连上，不需要重启。

> 二维码约 2 分钟过期。过期后再说一次「QQ登录」就会重新出码。

### 3.3 开启 OneBot11 服务

进 NapCat 的 WebUI（默认 `http://127.0.0.1:6099`）→ 网络配置 → 新建 **WebSocket 服务器**：

| 配置项 | 值 |
| --- | --- |
| 主机 | `127.0.0.1`（**千万不要填 `0.0.0.0`**） |
| 端口 | `3001` |
| Token | 建议设置，填到本项目的配置里 |
| 消息格式 | `array`（**必须**，否则收不到结构化消息） |

完成后 `/im status` 应显示：

```
🟢 QQ：online — 已连接 NapCat（机器人 <你的QQ号>）
```

### ⚠️ 换号时的两个经典坑

这两个坑都会表现成「二维码出不来 / 一直卡在等二维码」，但原因完全不同：

**坑一：给启动脚本传了 QQ 号**

用快速登录（`launcher.bat <QQ号>`）时，如果那个账号在本地已经是登录状态，QQ 内核会报
「当前账号已登录，无法重复登录」，然后**永远卡在等二维码**。

→ 想换号就用不带参数的方式启动（走二维码登录），或者直接用「发一次『QQ登录』」让本项目帮你处理。

**坑二：只重启 NapCat，没清登录票据**

QQ 客户端把登录票据存在系统数据目录里（Windows 是 `%APPDATA%\QQ\auth\login.enc`）。
**只重启不清票据**，客户端会带着旧会话起来，于是又回到坑一。

→ 正确顺序是：杀掉 QQ 与 NapCat 进程 → 清 `auth/login.enc` 与旧账号的分区目录 → 重新启动 NapCat。
本项目的「发『QQ登录』即换号」就是这个顺序，并且**清之前会先备份**。
想关掉这个行为：`channels.qq.switchAccount.enabled = false`。

## 4. 接入微信（可选）

在对话里说：

```
微信登录
```

二维码会出现在对话里，用微信扫。扫完你微信里会多一个 `@im.bot` 会话 —— 那就是机器人。

微信侧有几个**腾讯官方限制，绕不过去**：

| 限制 | 影响 |
| --- | --- |
| 凭据约 24 小时过期 | 过期后要重新扫码，通道会明确提示「登录已过期」 |
| 24 小时内最多 10 条主动消息 | 所以微信默认只回最终结果，不刷进度 |
| 一个机器人只能绑一个后台实例 | 绑到第二台机器会报错，需要先在微信里解绑 |

## 5. 把自己加进白名单（**最关键的一步**）

**默认谁都不理。** 这是刻意的安全设计。

先用手机发一句话，机器人会回：

```
你不在白名单里，无法调用本机 agent。
你的标识：123456789
请把这一行发给管理员，加入 <agentDir>/im-relay/config.json 后即可使用。
```

把那个标识填进配置：

```jsonc
{
  "channels": {
    "qq": {
      "allowUsers": ["123456789"],   // 私聊白名单
      "allowGroups": ["987654321"]   // 群白名单；群里默认需要真 @ 才响应
    },
    "wechat": {
      "allowUsers": ["xxxx@im.wechat"]
    }
  }
}
```

**改完即生效**（配置支持热加载），不用重启、不用 reload。

## 6. 发出第一句话

在手机上：

```
帮我看看这个目录下有什么
```

本机的 agent 会真的去读，然后把结果回到聊天窗口。

## 7. 写下你的工作约定

首次运行会生成 `<agentDir>/im-relay/AGENT.md`。它是**给 agent 看的工作约定**，
每条 IM 消息前都会被垫进上下文 —— 改它就能改行为，而且不会因为上下文压缩而丢失。

建议至少写清三件事：

1. **输出约定** —— 比如「结论超过 N 字就发 PDF，聊天里只留摘要」
2. **隐私红线** —— 哪些内容不允许发到公开位置
3. **安全红线** —— 比如「覆盖任何既有资料之前先备份」

这个文件的完整版路径会一起注入，所以你可以写得很长，agent 需要时会自己去读。

## 新手常见问题

| 现象 | 处理 |
| --- | --- |
| 发了消息没反应 | 先 `/im status` 看通道是否 online；再看白名单里有没有自己的标识 |
| QQ 显示 `needs-login` | 在对话里说一次「QQ登录」 |
| 二维码扫了没用 | 大概率是上面那两个换号坑之一 |
| 回复慢 | 本机 agent 在真的跑命令，慢是正常的；打开进度开关可以看到它在干什么 |
| 收不到文件 | 微信通道不支持发文件，只有 QQ 可以 |

# 第二部分 · 原理拆解

## 2.1 网络模型：为什么不需要内网穿透

IM 接入通常有两种模式，本项目选了第二种：

| 模式 | 做法 | 代价 |
| --- | --- | --- |
| Webhook（回调） | 平台把消息 POST 到你的公网地址 | 需要公网 IP 或内网穿透，还要对外暴露一个端点 |
| **长连接 / 轮询（本项目）** | 你的程序主动连出去，从平台拉消息 | 什么都不用配，但也拿不到平台的推送能力 |

所以这个项目里**没有任何入站监听端口**：

- **QQ**：NapCat 在本机以 WebSocket 服务端形式监听 `127.0.0.1:3001`，
  本扩展连过去 —— 全程不出本机
- **微信**：本扩展主动向腾讯 iLink 云发长轮询请求（纯出站 HTTPS）

攻击面因此只剩一个问题：**谁能给这个机器人发消息**。答案由白名单决定。

## 2.2 QQ 和微信的「机器人」是两种完全不同的东西

这一点必须搞清楚，否则很容易误解机器人的权限边界。

| | 微信 | QQ |
| --- | --- | --- |
| 协议侧 | 腾讯官方 iLink 通道 | 第三方 OneBot11 实现（如 NapCat） |
| 扫码做了什么 | 在腾讯云端**新建/绑定一个机器人身份** | **登录你已有的那个 QQ 号** |
| 是否产生新账号 | ✅ 有，就是那个机器人身份 | ❌ 没有，一个都不新建 |
| 「机器人」是谁 | 一个独立的 bot 账号 | **就是被登录的那个 QQ 号本身** |
| 怎么找到入口 | 微信里直接多出一个 bot 会话 | 没有新会话，得自己造场景（小号私聊/建群） |

**微信**：扫码 = 在你的微信里注册一个机器人身份，并把你机器上的程序授权成它的后台。
机器人只说自己的话，**不会**用你的身份发言，也读不到你的聊天记录 ——
它只能收到「你对它说的话」。

**QQ**：扫码 = 用你的 QQ 号登录了一个协议端。
所以那个号**就是**机器人：它发的每条消息都来自那个号，别人看到的就是它，
好友列表里也真的会显示「电脑在线」。

**实践建议**：QQ 侧用一个**专门的小号**当机器人，主号只做白名单里的主人。
用一个常用号当机器人，意味着那个号能收到的事件都会经过协议端。

## 2.3 一条消息的完整旅程

```
① 你在手机上发一句话
        ↓
② 平台（腾讯）把消息送到
   · QQ  ：NapCat 通过 WebSocket 推给本扩展
   · 微信：本扩展的长轮询从 iLink 云拉到
        ↓
③ Router 准入：白名单 → 去重 → 限流
        ↓
④ 入队。同一时刻只处理一条，其余排队（FIFO）
        ↓
⑤ 组装「垫话」：
   [相册回执] + 工作约定 + 身份定位 + 最近聊天记录 + 空间说说
        ↓
⑥ 注入 agent：垫话 + 你的原话（+ 图片）
        ↓
⑦ agent 真的去干活：读文件、跑命令、调工具
        ↓
⑧ agent 结束时，把最终答复回到**触发它的那个 IM 会话**
```

几个刻意的设计：

- **单并发**：同一时刻只让 agent 处理一条 IM 请求。这样「谁问的谁收到答案」是确定的，
  不会串台。
- **垫话在入队时就组装好**：这样重载时队列接力也能把上下文带过去。
- **回复只回给发起者**：一个 turn 的产出只回给触发它的那个会话。

## 2.4 为什么只在最后回一次

本项目的回复时机是「agent **彻底**跑完」（含重试与压缩重试），而不是在流式过程中反复发。

原因是微信侧一条硬限制：**24 小时内最多 10 条主动消息**。如果每调一次工具就回一条，
额度几分钟就烧光了。

需要在 QQ 上看实时进度的话，把 `channels.qq.progress` 设成 `live` —— QQ 没有这个额度限制。

## 2.5 记忆是怎么注入的

agent 的上下文会被压缩，早期对话会从窗口里消失。这个项目用**四层**来对抗：

| 层 | 内容 | 从哪来 |
| --- | --- | --- |
| 1 | 工作约定 | 本机文件 `AGENT.md`，你可以直接编辑 |
| 2 | 身份定位 | QQ 空间里正文以 `[身份]` 开头的那条说说 |
| 3 | **最近聊天记录** | 主动拉取 IM 侧的历史消息（默认最近 10 条） |
| 4 | 空间说说摘要 | 最近 N 条 + 历史抽样 M 条 |

**注入时机**（不是每条都塞，那样太贵）：

```
新会话开始 / 通道刚登录成功        → 必发一次完整记忆
每 N 条消息（默认 15，可配）      → 补发一次
其余消息                          → 不注入
```

**为什么聊天记录单独算一层**：pi 的上下文会被压缩，而 IM 侧的聊天记录是
**一份独立且完整的副本**，不受压缩影响。把它捞回来，长会话就能接上前文。

每个块都有独立预算（约定 35% / 身份 10% / 聊天记录 40% / 说说 15%），
所以「约定文件写得太长」不会把聊天记录挤掉。

读记忆失败一律静默降级（用缓存或直接跳过），**不会影响消息本身被处理**。

## 2.6 多会话与单通道

一个进程里可以同时开着多个 agent 会话，但 **IM 通道只有一套**。

如果每个会话各建一套通道，会出现：N 条 WebSocket 连着同一个协议端导致一条消息被回复 N 次、
长轮询互相抢游标、限流额度被 N 倍消耗。

所以：**通道是进程级的，会话只是参与者**。IM 消息只进「当前活跃会话」，
回复也只回到 IM。用 `/im attach` 可以把某个会话钉住。

# 第三部分 · 面向开发者

## 3.1 四个可移植的构件

这套设计里真正值得抄走的是这四层。换任何 agent 运行时，它们都能原样保留。

```
① Channel（通道）
   start() / stop() / status()
   send(target, text)
   sendFile?(target, path)     可选能力，没有就明确报「不支持」
   login?() / beginLogin?()    扫码登录
   api?()                      透传底层协议接口
   ⇒ 换 IM 平台只换这一层，上层完全不用动

② Router（准入与排队）
   白名单 → 去重 → 限流 → 队列(FIFO) → 单并发 → 回复只回发起者
   ⇒ 这是「能安全对外」的核心，不建议省

③ Memory（上下文垫层）
   每轮注入：本地约定文件 + 外部记忆源（本项目用 IM 聊天记录 + 空间说说）
   必须有长度上限；必须能降级；每块独立预算
   ⇒ 对抗上下文压缩的唯一实用手段

④ Outbound（出站能力）
   文件 / 长文转 PDF / 进度开关
   ⇒ 手机上看长文和表格很痛苦，PDF 是刚需
```

## 3.2 文件地图

```
extensions/im-relay/
├── index.ts            宿主入口：事件订阅、命令与工具注册、状态显示
├── router.ts           准入 → 排队 → 垫上下文 → 注入 agent → 回传
├── host.ts             进程级单例：多会话共享一套通道
├── config.ts           配置结构与默认值
├── watch.ts            配置热加载（目录监听 + 去抖 + 内容哈希）
├── memory.ts           记忆组装与注入策略
├── chatlog.ts          读最近 IM 聊天记录（长会话记忆）
├── qzone.ts            读 QQ 空间（走空间网页接口）
├── album.ts            收图落盘、按内容去重
├── md.ts / pdf.ts      Markdown → HTML → PDF
├── login-ui.ts         二维码按界面能力投递
├── qr.ts               二维码渲染（图片 / ASCII）
├── lock.ts             单实例锁（防止两个进程抢同一套通道）
├── store.ts            会话备注持久化
├── text.ts             文本工具
├── triggers.ts         对话里的确定性入口（「QQ登录」这类短语）
├── log.ts              日志
└── channels/
    ├── types.ts            Channel 接口与消息类型
    ├── qq.ts               QQ 通道：事件 → InboundMessage；send → 发消息
    ├── onebot11.ts         OneBot11 WebSocket 客户端
    ├── napcat-webui.ts     NapCat WebUI 客户端（扫码登录）
    ├── napcat-process.ts   换号：杀进程 / 清票据 / 重启
    ├── wechat.ts           微信通道：扫码登录 + 长轮询 + 发消息
    ├── ilink-client.ts     iLink HTTP 协议层
    └── ilink-types.ts      iLink 类型定义
```

运行时数据（**不在代码目录**）：`<agentDir>/im-relay/`
—— `config.json`（配置）、`AGENT.md`（工作约定）、`logs/`、`state/`、`tmp/`。

## 3.3 想改某个东西，该动哪一层

| 你想做的事 | 动哪里 |
| --- | --- |
| 支持一个新的 IM 平台 | 新增一个实现 `Channel` 接口的文件，然后在 `host.ts` 的 `registerChannels` 里注册 |
| 改白名单 / 限流 / 去重规则 | `router.ts` 的 `isWhitelisted` / `RateLimiter` / `DedupeSet` |
| 改「怎么给 agent 垫上下文」 | `memory.ts`（组装与预算）、`router.ts` 的 `buildNotes`（时机） |
| 改回复的格式 / 分段 | `router.ts` 的 `buildFinalReply`、`text.ts` |
| 加一个给 agent 用的工具 | `index.ts` 里 `pi.registerTool` |
| 加一个对话触发词 | `triggers.ts`（整句精确匹配，不做包含匹配，否则正常提问会被劫持） |
| 换 PDF 渲染方式 | `pdf.ts`（当前是 Chrome/Edge 无头打印） |
| 改记忆读什么 | `qzone.ts`（空间）、`chatlog.ts`（聊天记录） |
| 加配置项 | `config.ts` 的接口 + `DEFAULT_CONFIG`（加进默认值就会自动做深合并） |

## 3.4 实测踩出来的坑

这些都是真实撞过、而且**很难从表象看出来**的，迁移时值得直接照搬结论。

**1. 重载会吞掉当前那一轮的结果**

如果配置重载恰好发生在某轮消息处理中间，新建的 router 里没有「当前 job」，
结束回调就会直接跳过发送 —— 用户看到的是「agent 跑了半天，一个字都没回」。

→ 重载前先把「当前 job / 队列 / 回复目标」导出来，建好新的再装回去。

**2. 不能监听配置文件本身**

原子写是「写临时文件 + rename」。rename 之后原 inode 就没了，监听文件本身会**第一次改名就失联**。

→ 监听**目录**，再按文件名过滤。

**3. 半截 JSON 不能热加载**

有些实现对损坏配置的处理是「改名备份 + 回退默认值」。这个副作用放在热加载路径上很致命 ——
用户只是保存到一半被读到了，结果配置被备份走了。

→ 先做语法校验，不合法就跳过这一次。

**4. 协议端的事件可能只推给一条连接**

实测某些 OneBot11 实现，**事件只推给先连上的那条连接**，第二个客户端收不到
message 事件；但 **action 调用是每条连接独立可用的**。

→ 需要旁路读消息时用「主动拉历史」，不要指望监听事件。

**5. QQ 空间只能写、不能读**

协议端通常只暴露「发说说 / 删说说」，没有任何「读说说」的接口。

→ 要读就得自己拿 cookies 去调空间自己的网页接口。
另外：置顶接口在部分账号上不可用，而且说说列表**不返回「是否置顶」字段** ——
所以「用置顶说说当身份 prompt」这条路走不通，改用**正文标记**更稳。

**6. 发文件也必须按「最近说过话」路由**

不要做成能向任意账号推送 —— 那等于给你的机器开了一个对外发信器。

**7. 进程控制类的功能一定要能关掉、能干跑**

「换号」需要真的杀掉进程、删登录票据。这类功能必须：

- 清任何东西之前先备份
- 有配置开关能整体关掉
- 有干跑开关（本项目用环境变量），否则单测跑一遍就会把开发者本地的账号踢下线

## 3.5 开发与测试

```bash
npm install
npm test        # 全部用例
```

测试的取向是**锁死真实踩过的 bug**，而不是追求覆盖率数字。比较有代表性的几类：

- 同一进程多会话时，通道只启动一次
- 一条消息只被回复一次，且回到发起者
- 重载恰好撞上处理中间时，结果不丢
- 配置内容没变时不重载；半截 JSON 时跳过
- 聊天记录读不到时静默降级，不影响消息处理
- 换号逻辑全程干跑，不碰真进程

## 3.6 迁移到其它 AI Agent

| 构件 | 本项目（pi 扩展） | Claude Code | IDE 内 agent | 自研 agent loop |
| --- | --- | --- | --- | --- |
| 接入点 | 扩展（事件订阅 + 注册工具） | hooks + MCP server | 自定义命令 / MCP | 自己的事件循环 |
| 把 IM 消息交给模型 | 注入用户消息 | hook 返回额外上下文 | 拼进 prompt | 直接进 message 列表 |
| 把结果发回去 | 监听「跑完」事件 | hook 的结束事件 | 包装调用层 | 自己的结束回调 |
| 配置热加载 | 目录监听 + 内容哈希 | 同 | 同 | 同 |

关键不在「用哪个框架」，而在**把 IM 细节压在 Channel 层、把安全策略压在 Router 层**。
只要这两层是干净的，上面的 agent 运行时换什么都没关系。

### 如果你只想做三件事

1. 写一个干净的 **Channel 接口**（`send` / `sendFile` / `login` / `api`），IM 细节全关在里面
2. 写一个**默认拒绝**的 Router，并保证「回复只回给发起者」
3. 把约定写成一个**每轮注入的本地文件**，不要把行为约定寄托在模型的记忆上

# 第四部分 · 把 QQ 号经营起来

这一部分是这个项目最好玩的地方：**你不只是在接一个通道，你是在给 agent 一个可居住的账号。**

## 4.1 为什么值得经营

一个只会回消息的机器人，和一个有头像、有签名、有空间、说话前后一致的 agent，
体验差别很大。前者是个接口，后者是个「人」。

而且这件事是**可程序化**的 —— 协议端通常暴露了足够多的接口，让 agent 自己维护门面：

| 项 | 能做什么 |
| --- | --- |
| 头像 | 换成本机的图片文件 |
| 昵称 / 个性签名 | 直接改 |
| 在线状态 | 在线 / 忙碌 / 离开 / 各种趣味状态 |
| 空间说说 | 发布、删除、控制可见范围 |
| 空间读取 | 通过空间网页接口读回来 |

于是你可以让 agent **自己写日志、自己维护人设**，而它写下的东西又会成为它的记忆。这个闭环很有意思。

## 4.2 身份定位：一条带标记的说说

在空间里发一条正文以 `[身份]` 开头的说说，它会被当成**身份定位 prompt** 单独注入。

标记是可配的（`memory.identityMarker`）。为什么用标记而不是「置顶」：

- 协议端的置顶接口不一定可用
- 说说列表接口通常**不返回「是否置顶」字段**，就算置顶了也认不出来
- 标记法不依赖任何平台权限，也不会因为接口变动而失效

内容建议写清三件事：**我是谁、我的边界在哪、我做事的方式**。

## 4.3 空间即日志

把空间当 agent 的公开日志用。每天做完事记一条，好处是：

- 这些内容会自动进入它的上下文（说说摘要那层），等于**外置的长期记忆**
- 用户可以随时翻看它做过什么，比翻聊天记录直观
- 时间久了，它就有了「履历」

配合可见范围设置（见 4.5），可以做到「只有号主能看到」。

## 4.4 三层记忆的分工

| 层 | 载体 | 特点 | 适合放什么 |
| --- | --- | --- | --- |
| 短期 | IM 聊天记录 | 自动、完整、会滚动 | 最近聊了什么 |
| 中期 | 空间说说 | 可读可写、有可见范围控制 | 日志、阶段结论、做过的事 |
| 长期 | 本机约定文件 | 用户可编辑、每轮注入 | 行为约定、环境备忘、红线 |

三层的注入都有限长与预算，读不到都会静默降级 —— **记忆是增强，不是依赖**。

## 4.5 隐私红线

**默认只对号主可见，不公开发。** 空间说说的可见范围要显式设置成「部分好友可见 → 仅号主」。

另外几条建议写进约定文件：

- 不把聊天内容、文件路径、账号信息发到任何公开位置
- 版本库、截图、日志里也不要出现真实账号与私人路径
- 覆盖任何既有资料之前先备份（这条通常都是被教训出来的）

## 4.6 一个务实的顺序

1. 先把通道打通，能收发消息
2. 写 `AGENT.md`，把输出约定和安全红线定下来
3. 设头像、昵称、签名 —— 让账号**看起来**是活的
4. 发一条 `[身份]` 说说，把定位固定下来
5. 开始用空间记日志，让它积累自己的历史

第 3、4、5 步都可以在对话里让 agent 自己完成。

## 安全模型

IM 驱动的是**你本机真实权限的 agent**：它能读写你的文件、执行你的命令。所以：

1. **默认拒绝** —— 白名单为空时，任何人发消息都不会被处理
2. **白名单分级** —— 私聊白名单 + 群白名单；群里同时配了用户白名单时，发言人也要在内
3. **只监听回环** —— 协议端必须绑 `127.0.0.1`，否则局域网内任何人都能伪装成消息
4. **去重 + 限流** —— 事件级去重 + 滑动窗口限流
5. **凭据落盘权限收紧**，日志不打印 token
6. **无公网暴露** —— 没有任何入站监听端口
7. **出站只能回给「最近说过话的人」** —— 没有向任意账号推送的入口
8. **破坏性操作先备份** —— 换号、清登录态这类操作一律先备份，且可整体关闭

> 对外提供服务前请自行评估合规要求。使用本项目接入 IM 平台，需自行确保符合对应平台的服务条款。

## 故障排查

日志在 `<agentDir>/im-relay/logs/`，或在对话里执行 `/im log` 拿路径。

| 现象 | 原因与处理 |
| --- | --- |
| 状态显示「已被其它进程占用」 | 同时开了两个 agent 进程。`/im status` 会告诉你是哪个 pid，关掉那个 |
| 手机发消息收到「没有活跃会话」 | 会话登记丢了（界面重连等边界情况）。执行 `/reload` 即可恢复 |
| QQ 状态 `error`，提示协议端不可达 | 协议端没启动、OneBot11 服务没开、或端口/Token 不匹配 |
| QQ `needs-login` | 协议端活着但 QQ 没登录，说一次「QQ登录」 |
| 二维码出不来 / 卡在等二维码 | 见第一部分「换号时的两个经典坑」 |
| 收到消息但机器人不回 | 白名单没配 |
| 群里怎么 @ 都不理 | `groupTrigger` 是 `mention` 时需要真 @；且群号要在 `allowGroups` 里 |
| 微信 `needs-login` | 凭据过期（约 24h），重新扫码 |
| 微信回复被拒 | 超过 24h 内 10 条主动消息额度，或上下文令牌失效；让对方先发一条即可恢复 |
| 结论里出现 Markdown 符号 | 回传前会做 Markdown → 纯文本转换，代码块内容保持原样 |
| 配置改了不起作用 | 确认 JSON 合法；不合法时热加载会跳过（日志里有记录） |
